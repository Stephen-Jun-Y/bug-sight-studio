# 个人中心真实化设计文档

## 背景

当前项目的识别主链路、双语百科、搜索/收藏/历史记录已经接入真实后端，但“我的”相关能力仍以原型页面为主：

- `/profile` 只读取本地昵称，统计卡是静态值
- `/edit-profile` 只有表单 UI，没有真实读写
- `/change-password` 只有前端校验，没有真实提交
- `/settings` 里的退出登录、注销账号、绑定手机都还是展示态

后端已经提供了可复用的真实用户接口：

- `GET /users/me`
- `PATCH /users/me`
- `POST /users/me/password`
- `DELETE /users/me`

因此本轮目标是用**最小改动**把个人中心核心能力真实化，并顺手把“我的”页顶部资料与统计变成真实数据。

## 目标

本轮完成以下能力：

1. “我的”页真实展示当前用户资料
2. “我的”页统计卡基于现有识别记录接口实时计算
3. 编辑资料页支持真实加载与保存
4. 修改密码页支持真实提交
5. 设置页支持退出登录与注销账号
6. 绑定手机页明确展示“暂未开放”

## 不在本轮范围内

以下内容本轮不做，避免范围失控：

- 头像真实上传
- 成就徽章真实化
- 观察地图真实化
- 消息通知真实化
- 手机绑定后端能力
- 新增后端聚合统计接口
- 引入全局状态库进行重构

## 方案选择

### 方案 1：最小改动接真接口
- 保留现有页面结构和交互风格
- 页面内部直接调用真实 service
- 本地登录缓存只做必要同步

优点：风险最低、交付最快、和现有代码风格一致。
缺点：用户数据逻辑会分散在几个页面中。

### 方案 2：个人中心真实化 + 我的页统计真实化（采用）
- 在方案 1 的基础上，把 `/profile` 顶部资料与统计一起接真数据
- 统计通过现有 `/recognitions` 列表推导，不新增后端接口

优点：用户感知更完整，答辩时更像完整产品。
缺点：统计精度依赖前端计算和当前分页范围。

### 方案 3：统一全局用户状态层
- 新增全局用户 store/context
- 所有用户资料页统一从全局状态读取与刷新

优点：长期最好维护。
缺点：这轮范围过大，不符合当前“小步快跑”的目标。

## 采用方案

采用**方案 2**。

策略是：

- 不改后端接口设计
- 不大改现有 UI
- 只在前端补足真实 service、页面提交和本地缓存同步
- 统计卡基于现有历史识别数据做前端聚合

## 页面与行为设计

### 1. 我的页 `/profile`

#### 当前问题
- 只显示本地昵称
- 统计卡是静态数字
- “退出登录”按钮没有真实行为

#### 本轮行为
- 进入页面后调用 `GET /users/me` 拉取当前用户资料
- 头像仍沿用现有占位展示；若后端将来返回 `avatarUrl`，则优先显示真实头像
- 统计卡基于 `/recognitions` 列表前端计算：
  - `物种`：按 `species.id` 去重后的识别物种数
  - `地点`：非空 `location` 去重后的地点数
  - `天数`：按 `capturedAt` 的日期去重后的观察天数
- 顶部描述文案改为基于真实统计值生成
- “退出登录”按钮接入真实退出行为

#### 风险与限制
- 因为当前历史列表接口分页，统计卡默认按“第一页记录”计算，属于**最小真实化**。
- 如果后续需要全量精确统计，再考虑后端补聚合接口。

### 2. 编辑资料页 `/edit-profile`

#### 当前问题
- 表单内容写死
- 保存按钮没有真实提交

#### 本轮行为
- 页面加载时调用 `GET /users/me`
- 表单字段映射为：
  - `nickname`
  - `bio`
  - `location`
- 点击保存时调用 `PATCH /users/me`
- 保存成功后：
  - toast 成功提示
  - 同步刷新本地缓存中的用户昵称/头像
  - 返回上一页或跳回 `/profile`

#### 非目标
- 不做头像上传
- 所在地继续保持文本输入/按钮形式，不新增地区选择器

### 3. 修改密码页 `/change-password`

#### 当前问题
- 只有前端密码强度和一致性校验
- 没有真实请求

#### 本轮行为
- 继续保留现有密码强度校验与交互
- 提交时调用 `POST /users/me/password`
- 请求字段与后端 `ChangePasswordRequest` 对齐
- 成功后显示 toast，并返回设置页
- 失败时展示后端错误文案；英文模式由现有前端错误映射层处理常见提示

### 4. 设置页 `/settings`

#### 当前问题
- 退出登录和注销账号按钮都没有真实行为
- 绑定手机入口会造成“能用”的误导

#### 本轮行为
- 保留语言切换和通知开关现状
- “退出登录”：
  - 清理 token、本地用户缓存
  - 跳转到 `/auth`
- “注销账号”：
  - 先弹出二次确认
  - 调用 `DELETE /users/me`
  - 成功后清理登录态并跳转 `/auth`
- “绑定手机”：
  - 保留入口不删除
  - 页面内明确显示“暂未开放”

### 5. 绑定手机页 `/bind-phone`

#### 当前问题
- 当前页面像真功能，但后端并未提供完整能力

#### 本轮行为
- 页面改为说明态：
  - 展示“暂未开放”
  - 简短说明后续会支持手机号绑定与安全验证
- 不显示会误导用户的提交成功预期

## 数据与接口设计

### 新增前端 service

新增：`src/services/user-service.ts`

包含：
- `getCurrentUserProfile()` -> `GET /users/me`
- `updateCurrentUserProfile(payload)` -> `PATCH /users/me`
- `changeCurrentUserPassword(payload)` -> `POST /users/me/password`
- `deleteCurrentUser()` -> `DELETE /users/me`

### 本地登录缓存同步

扩展 `src/lib/auth.ts`：
- 保留现有 `saveAuth()` / `clearAuth()`
- 新增一个轻量方法用于在资料更新后同步本地用户缓存，例如：
  - `updateStoredUser(partialUser)`

用途：
- 编辑资料保存成功后，让 `/profile` 和其他页面立刻拿到新的昵称/头像
- 不需要重新登录即可刷新本地展示

### 类型扩展

在 `src/types/api.ts` 中补足：
- 当前用户资料请求/响应类型
- 修改密码请求类型
- 编辑资料请求类型

需要和后端 `/users/me` DTO 保持一致。

## 错误处理策略

- 未登录 / token 失效：沿用现有 API client 的处理策略，必要时清理登录态并跳转 `/auth`
- 编辑资料失败：toast + 保留表单内容
- 修改密码失败：toast，停留在当前页
- 注销失败：toast，不主动清理本地登录态
- 用户资料加载失败：
  - `/profile` 给出页面内空态/错误提示
  - `/edit-profile` 给出加载失败提示，并保留返回

- 保存成功后同步本地用户缓存

3. `ChangePasswordPage`
- 表单合法时发起真实请求
- 请求 payload 与后端字段一致

4. `SettingsPage`
- 点击注销账号会调用删除接口并清理登录态

5. `BindPhonePage`
- 页面展示“暂未开放”文案

最终验证：

## 验收标准

满足以下条件即视为本轮完成：

1. 登录后进入“我的”页，可看到真实昵称与基于历史记录计算的统计值
2. 编辑资料后，返回个人页可立即看到最新昵称/资料
3. 修改密码可真实提交并成功返回
4. 点击退出登录后返回登录页，且本地 token 被清除
5. 点击注销账号后，后端账号被删除，本地登录态被清除
6. 绑定手机页面明确显示“暂未开放”
7. 前端测试与构建通过
